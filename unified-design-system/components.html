Button 01 live

diet-guard/app/lib/screens/meal_builder_screen.dart

Radius: radius-sm, 8px. Same token as inputs and chips — one family of interactive elements, not a size picked for buttons alone.

Padding: 24px / 12px. Horizontal is exactly 2× vertical (rule 22) — never tuned per component.

Label: 16px, body. A button is read, not decorative chrome — never below the 16px floor.

Fill only, no shadow. Dark surfaces never carry a shadow — weight comes from the fill itself.

Card 02 live

diet-guard/app/lib/widgets/day_status_calendar.dart

✓
!

Radius: radius-md, 12px. One step up from a button's 8px — a card contains interactive elements, so it must read as a larger unit than they are.

Elevation: fill step, not shadow. surface-1 against the page background — dark surfaces never use a shadow for depth.

Nested radius: 6px. Rule 24 — inner cell radius = outer (12px) − the gap to its edge (≈6px), not a reused constant.

Status cells use on-fill. The ✓/! cells sit directly on success/danger — this is the one place in the app that already got the on-fill rule right.

The status colors sit at mid brightness, so ink gives strong on-palette contrast — this is the real code comment in day_status_calendar.dart, written before today's on-fill token existed to name the pattern.

Switch 06 spec only

no live usage yet — locking the values in before the first one gets built

Track = accent, thumb = on-fill. Same fill/on-fill pairing as a button — a switch is a tiny filled control, not a new color relationship to invent.

Fully rounded track. The one place in this system a pill shape is correct: an on/off track has no other elements to stay visually consistent with, unlike a button.

Off state: track becomes surface-2, thumb becomes muted — a fill-step change, matching how every other "inactive" state in this system works (never a separate grey palette).

Checkbox 08 live

dufs-cloud/web/src/index.css — .tile-select

Chip sits on a scrim, not a fill. rgba(ink,0.45) over a photo thumbnail — this is on-scrim territory, not on-fill, since the thumbnail behind it varies.

Open finding: the checkbox itself is an unstyled native <input type="checkbox"> — its checked-state color is the browser's default blue, off-palette. No custom checkbox styling exists yet.

The 8px-radius scrim chip behind it is deliberately correct (matches radius-sm, dark translucent per the scrim rule) — only the checkbox glyph inside it is unstyled.
